# DataSherlock Harness MVP 范围与成功指标

**版本：** v0.1  
**状态：** 已确认，作为第一阶段开发边界  
**适用阶段：** 第 1 周数据环境至第 8 周交付

## 1. 目标

DataSherlock Harness 的第一版只解决一个问题：

> 当 SaaS 运营指标出现异常时，系统能够在本地模拟数据环境中，使用受控的只读查询和数据质量检查，定位最可能的数据管道或数据质量根因，并输出带证据的修复建议。

第一版优先证明诊断闭环可靠可复现，而不是追求覆盖所有业务问题或实现完全自动化修复。

## 2. 用户与使用场景

| 项目 | MVP 定义 |
| --- | --- |
| 主要用户 | 数据分析师、数据工程师、负责数据质量的运营人员 |
| 数据场景 | 模拟 SaaS 平台的用户、事件、订阅、实验分流和日指标数据 |
| 异常来源 | 人工创建或接口传入的单个指标异常告警 |
| 运行环境 | 本地 DuckDB 数据库和本地文件；Docker 用于统一启动环境 |
| 处理目标 | 诊断数据系统或数据管道导致的指标异常，并给出可审阅的修复建议 |

## 3. 输入、处理与输出

### 3.1 输入

每一次诊断从一条结构化告警开始。最小输入字段如下：

```json
{
  "incident_id": "INC-001",
  "metric": "daily_active_users",
  "observed_at": "2026-08-12",
  "expected_value": 10000,
  "observed_value": 7600,
  "change_rate": -0.24,
  "severity": "high"
}
```

输入还包括：

- SaaS 模拟数据及其表结构；
- 指标语义配置，例如指标的计算口径、依赖表和可下钻维度；
- 工具权限与资源限制配置，例如 SQL 只读、最大查询次数和超时；
- Benchmark 故障案例的标准答案，仅用于评测，不直接提供给诊断 Agent。

### 3.2 处理范围

系统按明确的状态流转执行：接收告警、判断异常、制定调查计划、调用受控工具、验证根因假设、输出结论与修复建议。所有 SQL、工具调用、证据和状态变化都要保留记录，以便复现和审计。

### 3.3 输出

每次诊断必须输出结构化结果，而不是只输出一段自然语言。最小输出字段如下：

```json
{
  "incident_id": "INC-001",
  "status": "ROOT_CAUSE_FOUND",
  "root_cause_type": "missing_partition",
  "affected_asset": "events_mobile_20260812",
  "confidence": 0.94,
  "evidence": [
    {
      "evidence_id": "E01",
      "finding": "移动端事件量较过去 7 日均值下降 92.4%"
    },
    {
      "evidence_id": "E02",
      "finding": "目标分区更新时间停留在前一天"
    }
  ],
  "proposed_fix": {
    "action": "rerun_partition",
    "target": "events_mobile_20260812"
  }
}
```

输出必须满足以下规则：

- 每个根因结论至少有 2 条相互独立的证据；
- 证据必须能追溯到具体 SQL 结果、质量检查结果或管道检查结果；
- 任何修复建议都只描述或在沙箱中执行，不能直接修改生产数据；
- 无法形成充分证据时，状态必须为 `UNRESOLVED`，不能猜测为已解决。

## 4. MVP 不做什么

以下内容明确不属于第一版范围：

- 通用 BI 问答、任意自然语言取数和报表生成；
- 接入真实生产数仓、生产写权限或自动修改生产数据；
- 多行业、多租户或企业级权限体系；
- 不经过人工审批的自动修复；
- 多 Agent 自由讨论、复杂 RAG 知识库或长链路自治；
- 业务策略、营销效果或用户行为变化的开放式归因；
- 首批 6 类故障之外的故障自动诊断承诺。

业务真实变化可以作为“非数据故障”的排除方向被记录，但 MVP 不要求判断具体业务策略是否正确。

## 5. 核心指标定义

### 5.1 被诊断的业务指标

| 指标 | 英文字段 | 定义 | 主要依赖数据 |
| --- | --- | --- | --- |
| 日活用户数 | `daily_active_users` | 当天至少发生一次有效事件的去重用户数 | `events`、`users` |
| 新增用户数 | `new_users` | 当天完成注册的用户数 | `users` |
| 付费用户数 | `paid_users` | 当天处于有效付费订阅状态的去重用户数 | `subscriptions` |
| AI 任务次数 | `ai_task_count` | 当天 `run_ai_task` 事件数 | `events` |
| 平均会话时长 | `average_session_duration` | 当天有效会话的平均时长，单位为秒 | `events` |
| 转化率 | `conversion_rate` | 当天完成付费的去重用户数除以当天活跃去重用户数 | `subscriptions`、`events` |

指标口径和依赖关系必须由 `config/metrics.yaml` 统一管理；任何代码都不能各自硬编码另一套口径。

### 5.2 MVP 成功指标

| 成功指标 | 定义 | 第一版验收目标 |
| --- | --- | --- |
| Root Cause Top-1 Accuracy | 最终首选根因与标准答案一致的案例占比 | 不低于 80% |
| Affected Asset Accuracy | 受影响表、分区或任务与标准答案一致的案例占比 | 不低于 85% |
| Evidence Completeness | 满足“至少 2 条独立且可追溯证据”的已解决案例占比 | 100% |
| Invalid SQL Rate | 被 SQL 安全校验拒绝或执行失败的 SQL 占全部 SQL 的比例 | 不高于 5% |
| Unsafe Action Rate | 尝试执行非只读 SQL 或越权工具调用的次数占全部调用的比例 | 0% |
| Recovery Rate | 在检查点中断后可恢复并完成或明确终止的任务占比 | 不低于 90% |

上述指标在首批 6 类故障的 Benchmark 集上统计。首周先固定定义和数据口径；具体样本数、自动评测脚本和报告在后续 Benchmark 周实现。

## 6. 首批 6 类故障

首批故障只覆盖典型数据系统异常，选择原则是：可注入、可观察、可用受控工具验证、可形成清晰证据链。

| 编号 | 故障类型 | 根因标识 | 典型表现 | 最小证据 |
| --- | --- | --- | --- | --- |
| F01 | 分区缺失 | `missing_partition` | 指标在单日或单端突然下降 | 分区不存在或未更新；对应维度事件量显著下降 |
| F02 | 批次重复导入 | `duplicate_batch` | 事件量、任务次数或用户行为量异常升高 | 相同 `batch_id` 或事件键重复；重复率异常 |
| F03 | 空值异常 | `null_value_anomaly` | 去重用户、转化率或维度统计异常 | 关键字段空值率突增；空值集中于异常时间窗 |
| F04 | 数据延迟 | `data_delay` | 当天指标下降，后续日期回补 | 表或分区新鲜度低于阈值；上游任务未完成或延迟 |
| F05 | 时区错误 | `timezone_error` | 小时峰值整体偏移，日边界统计异常 | 事件时间分布偏移；时间转换或分区时间不一致 |
| F06 | 单位错误 | `unit_error` | 会话时长等数值型指标被系统性放大或缩小 | 数值分布偏离历史；单位换算与指标口径不一致 |

首批案例必须记录以下 Ground Truth：故障编号、受影响资产、受影响指标、预期根因、预期证据和可接受的修复动作。

- [x] 已定义 6 个核心业务指标及统一配置原则。

## 8. 后续依赖

本文件确认后，后续任务应以此为输入：

1. 数据工程实现模拟数据生成器、DuckDB 表结构和 `metrics.yaml`；
2. 工具层实现只读 SQL 执行、数据质量检查和相应安全限制；
3. Harness 实现状态机、假设管理、检查点和证据绑定；
4. Benchmark 为 F01-F06 建立故障注入、标准答案和评测报告。
